# Kudaibergen — Бизнес-логика

Чистая логика платформы: роли, сущности, флоу, правила, статусы. Без UI и дизайна —
за этим в `DESIGN_TOKENS.md` / `DESIGN_SPEC.md`. Детальный сценарий Quick Request
(шаг за шагом, с примерами) — в `TZ_BUSINESS_FLOW.md`, здесь только его место в общей картине.

---

## 1. Что это

Маркетплейс автозапчастей и авто. Регион — Бишкек (Кыргызстан), язык — русский.
Соединяет покупателей (владельцев авто) с продавцами (магазины запчастей, СТО,
частники) через **запросы (Request)** и **предложения (Offer)**, а не через
классическую витрину «каталог → корзина».

Ключевая проблема, которую решает продукт: сейчас продавцы получают заявки
вперемешку в WhatsApp, Instagram, звонках — и часть теряют. Платформа сводит все
заявки в одну очередь внутри приложения.

---

## 2. Роли

### 2.1 Покупатель (Buyer)
- Владелец автомобиля (может привязать несколько машин к профилю)
- Либо ищет готовое объявление (Store/CarListing), либо создаёт запрос (Request)
- Получает предложения (Offer) от продавцов, выбирает одно
- Общается через чат, договаривается о встрече/доставке, оставляет отзыв

### 2.2 Продавец (Seller)
- Магазин, СТО или частный продавец, привязан к Store (профиль магазина)
- Видит входящие запросы покупателей в своих категориях/по своим авто-маркам
- Отвечает предложением (цена, условия, срок)
- Ведёт инвентарь (Product), смотрит аналитику по своим сделкам

Роль выбирается один раз при регистрации и определяет весь дальнейший роутинг
(`(buyer)` vs `(seller)` в `src/app`). Смена роли — отдельная фича, сейчас не
предусмотрена.

## 3. Ключевые сущности (без учёта UI-полей)

| Сущность | Смысл |
|---|---|
| **User** | учётная запись, `role: buyer \| seller`, телефон — основной идентификатор |
| **Vehicle** | автомобиль покупателя (марка, модель, год, объём, привязан к User) |
| **Store** | профиль продавца: название, категории, адрес/филиалы, режим работы, рейтинг |
| **Product** | позиция в инвентаре продавца (деталь, цена, наличие) |
| **CarListing** | готовое объявление о продаже авто (прямая витрина, без Request) |
| **Request** | запрос покупателя: что нужно, для какого авто, бюджет, срочность, срок жизни |
| **Offer** | предложение продавца на конкретный Request: цена, условия, доставка |
| **Chat / Message** | переписка, привязанная к Offer или к CarListing/Store |
| **Review** | отзыв покупателя о продавце после сделки |
| **Notification** | системное событие, требующее внимания пользователя |

Связь: **Request 1—N Offer**, **Offer 1—1 Chat** (чат открывается только после
того, как покупатель выбрал предложение — не раньше).

## 4. Основные флоу

### 4.1 Прямая покупка (витрина)
```
Buyer: Home → открывает CarListing/Store → видит цену и продавца
     → жмёт "Написать" → открывается Chat напрямую со Store
     → переговоры → сделка вне приложения → Review
```
Используется, когда товар/авто уже выставлен продавцом как готовое объявление.
Request здесь не создаётся — это не аукцион, а обычная витрина.

### 4.2 Запрос → Предложения (Request/Offer)
```
Buyer:  создаёт Request (деталь/авто, для какой машины, бюджет, срочно/нет)
   →    Request публикуется продавцам, чьи категории/марки совпадают
   →    Seller видит Request в своей очереди, присылает Offer
   →    Buyer видит список Offer (цена, рейтинг продавца, срок доставки)
   →    Buyer выбирает один Offer → открывается Chat
   →    остальные Offer автоматически помечаются "не выбрано"
   →    переговоры → сделка → Review продавцу
```
Это основной сценарий для "ищу нестандартную деталь / не знаю у кого спросить".
Детальная пошаговая версия этого флоу (Quick Request) — в `TZ_BUSINESS_FLOW.md`.

### 4.3 Жизненный цикл Request
```
active (24–72 часа) → expired (без ответов, авто-закрытие)
                    → closed (buyer выбрал Offer)
                    → cancelled (buyer отменил вручную)
```
- Пока `active` — новые Offer принимаются.
- После `closed`/`expired` — Request уходит в архив, доступен только для истории.
- Один и тот же Request нельзя переоткрыть — только создать новый.

### 4.4 Жизненный цикл Offer
```
sent → viewed (buyer открыл) → accepted (buyer выбрал → Chat создаётся)
                             → rejected (buyer выбрал другого)
                             → expired (Request закрылся без ответа продавца)
```

### 4.5 Чат
- Создаётся автоматически при `Offer.accepted` или при первом сообщении со Store.
- Живёт, пока есть активность; авто-архивация после 30 дней тишины.
- Что может отправлять пользователь: текст, фото; голосовые — опционально, не в MVP.
- Внутри чата доступна карточка сделки (цена/условия из Offer) — это не отдельная
  сущность, а сниппет из Offer, подтягиваемый в шапку чата.

---

## 5. Правила видимости запроса

- Request видят только продавцы, у которых Store.categories пересекаются с
  категорией запроса **или** у которых в инвентаре есть подходящая марка/модель.
- Срочные (`urgent: true`) Request поднимаются в начало очереди продавца.
- Buyer видит только те Offer, что пришли на его собственные Request — чужие
  запросы и чужие сделки не видны никому, кроме модератора.

## 6. Рейтинг и доверие

**Рейтинг продавца**
- 1–5 звёзд, считается по Review после сделки.
- Отображается только после ≥5 завершённых сделок (иначе — "новый продавец").
- Свежие отзывы весят больше старых (экспоненциальное затухание, не линейное среднее).

**Статусы доверия продавца**
| Статус | Условие |
|---|---|
| Новый | только зарегистрировался, верификация не пройдена |
| Проверенный | прошёл верификацию (телефон + документ/ИНН) |
| Партнёр | долгосрочный, высокая конверсия и рейтинг ≥4.5 |
| Заблокирован | нарушение правил, жалобы подтверждены модератором |

**Критерии оценки в Review**: соответствие описанию, качество, честность цены,
скорость ответа, удобство встречи.

## 7. Уведомления — правила, когда триггерятся

| Кому | Событие |
|---|---|
| Buyer | пришёл новый Offer на его Request |
| Buyer | новое сообщение в чате |
| Buyer | Request скоро истекает (за 2 часа до expired), а Offer ещё нет |
| Seller | новый Request в его категории/марке (с приоритетом, если urgent) |
| Seller | новое сообщение от покупателя |
| Seller | Offer скоро "протухнет" вместе с Request |
| Оба | напоминание оставить Review через 24 часа после последнего сообщения в чате |

Правило анти-спама: не более одного пуша на одно и то же событие за 15 минут
(агрегировать, а не слать по одному на каждое сообщение).

## 8. Модерация и ограничения

- Номер телефона подтверждается по SMS при регистрации; для продавца дополнительно
  нужна проверка организации (ИНН или фото документа) для статуса "Проверенный".
- В чате запрещены: оскорбления, ссылки на внешние ресурсы, повторная отправка
  контактов после того, как стороны уже обменялись (защита от увода сделки в обход
  платформы — если это станет платным).
- Жалоба (Buyer↔Seller) → в очередь модератора → решение: предупреждение / бан /
  ничего. Пока без автоматизации, ручной разбор.
- Rate limit на создание Request: не более N активных одновременно на одного Buyer
  (защита от спама одинаковыми запросами разным продавцам).

---

## 9. Монетизация (пока не реализовано, зафиксировано на будущее)

- Комиссия с сделки не берётся напрямую (сделка — вне приложения, наличными/переводом),
  поэтому основная модель — **подписка для продавцов**, а не комиссия.
- Premium для продавца: приоритет в очереди Request, расширенная аналитика, бейдж.
- Разовое продвижение конкретного объявления/Store в топ категории.
- Комиссия появится только если добавится оплата внутри приложения (Phase 3+).

---

## 10. Что сознательно не входит в MVP

- Оплата внутри приложения.
- Доставка/логистика как отдельный сервис — только поле "самовывоз/доставка" в Offer.
- Мультиязычность (только русский).
- Автоматическая модерация текста/фото.
